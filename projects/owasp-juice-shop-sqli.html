01

Objective

The objective of this project was to practise identifying and validating SQL injection within an application intentionally designed for security training.

The exercise focused on understanding the relationship between user-controlled input, application requests and backend database queries rather than treating SQL injection as only a payload-based attack.

02

Lab Environment

OWASP Juice Shop Burp Suite Browser DevTools HTTP SQL Injection Web Security Input Validation Authentication Testing

OWASP Juice Shop was used as the target because it is intentionally vulnerable and designed for legal application-security training.

03

Methodology

  1. Application Mapping

    Reviewed accessible application functionality and identified locations where user-controlled input was submitted to the server.

  2. Request Interception

    Used Burp Suite to inspect HTTP requests and understand how application input was transmitted to backend functionality.

  3. Input Behavior Testing

    Modified input values inside the training environment and observed differences in application responses.

  4. Vulnerability Identification

    Identified behavior consistent with unsafe handling of input in backend database queries.

  5. Controlled Validation

    Confirmed the weakness only to the level required to demonstrate security impact inside the intentionally vulnerable lab.

  6. Impact Analysis

    Considered how equivalent weaknesses in a real application could affect authentication, confidentiality and database integrity.

  7. Reporting

    Documented the affected functionality, observed behavior, impact and recommended defensive controls.

04

Finding

WEB-003

SQL Injection in Application Input

HIGH

Testing within the intentionally vulnerable application demonstrated that user-controlled input could influence backend SQL logic. This illustrates the risk created when untrusted input is incorporated into database queries without safe parameterization.

ATTACK SURFACE

Application functionality accepting user-controlled values that were processed by backend database logic.

IMPACT

In a real application, SQL injection may allow unauthorized access to information, authentication bypass, modification of database content or other database actions depending on the application's privileges.

ROOT CAUSE

Unsafe construction of database queries using untrusted application input.

REMEDIATION

Use parameterized queries or prepared statements, enforce authorization independently of user input and apply least privilege to database accounts.

07

Remediation

  • Use parameterized queries or prepared statements for database operations.
  • Never construct SQL queries by directly concatenating untrusted application input.
  • Apply server-side validation as an additional defensive control.
  • Use least-privilege database accounts so application compromise does not automatically provide unrestricted database permissions.
  • Implement authorization checks independently of client-supplied values.
  • Avoid exposing detailed database errors to application users.
  • Include SQL injection testing in secure development and application security review processes.
08

Lessons Learned

  • SQL injection is fundamentally an input-to-query trust problem.
  • Understanding HTTP requests helps reveal how browser input reaches backend application functionality.
  • Burp Suite provides visibility into application behavior that is not always obvious from the user interface.
  • Successful validation should demonstrate risk without performing unnecessary actions beyond the assessment objective.
  • Remediation guidance is an essential part of professional penetration-testing work.
